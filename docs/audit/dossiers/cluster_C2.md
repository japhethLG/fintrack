# Cluster C2

Occurrence ID derived from the weekend-ADJUSTED date -> ID collisions/instability across periods

Source files implicated:
- app/lib/logic/projectionEngine/occurrenceIdGenerator.ts
- app/lib/logic/projectionEngine/incomeProjections.ts

## Member findings (from first-round analysts)

### [F2] (critical/logic-error) Semi-monthly occurrence IDs computed from the weekend-adjusted date collapse two distinct paydays into one ID (and one onto the same calendar day)
- File: app/lib/logic/projectionEngine/occurrenceIdGenerator.ts : 37-45
- Why wrong: calculateOccurrences pushes weekend-ADJUSTED dates (occurrenceCalculator.ts line 121), and incomeProjections/expenseProjections then call generateOccurrenceId with that adjusted Date. So getSemiMonthlyIndex receives the post-adjustment day, which is usually NOT one of specificDays, triggering the fallback. For the spec's default [15,30] with weekendAdjustment='after', when the 15th is a Saturday it moves to the 17th; `17 <= 15` is false, so it returns slot 2 — the SAME index as the 30th (slot 2). Both paydays then get the identical occurrenceId `src_YYYY-MM-2`. The index must be derived from the LOGICAL (pre-adjustment) scheduled day, not the shifted one. Consequence in projectionMerger: occurrenceId is the merge key; if the user completes/stores the first payday, its occurrenceId matches and shadows the second payday's projection, so the second paycheck silently disappears from the forecast; an OccurrenceOverride keyed by that ID also applies to both occurrences.
- Scenario: Salary, frequency 'semi-monthly', specificDays default [15,30], weekendAdjustment 'after', March 2025 (the 15th is a Saturday). Verified via node: day15 -> adjusted 2025-03-17 -> semiIdx 2 -> occId 'src_2025-03-2'; day30 -> adjusted 2025-03-31 -> semiIdx 2 -> occId 'src_2025-03-2'. Both paychecks share one ID. Marking the mid-month paycheck complete causes the end-of-month paycheck to vanish from projections (income understated by one full paycheck that month). Correct: two distinct IDs (slot 1 and slot 2) so both paychecks persist independently.
- Suggested fix: Compute the semi-monthly slot index from the un-adjusted logical occurrence (pass the pre-weekend-adjustment date to generateOccurrenceId, or pass the slot index/original day through), so the 15th is always slot 1 and the 30th always slot 2 regardless of weekend shifting.
- First-round verification: 3 votes, 0 refutes

### [F8] (high/correctness) Weekend adjustment can produce colliding occurrence IDs / scheduled dates for weekly and daily schedules, causing duplicate or double-counted occurrences and corrupt stored/projected merging
- File: app/lib/logic/projectionEngine/occurrenceIdGenerator.ts : 67-73
- Why wrong: calculateOccurrences computes the raw recurrence date and then applies adjustForWeekend BEFORE the date is passed to generateOccurrenceId (see incomeProjections.ts:36-44 and occurrenceCalculator.ts:75/98 where adjustForWeekend wraps the pushed date). generateOccurrenceId then derives the stable key from the already-adjusted date. For 'weekly', a Sunday occurrence with weekendAdjustment 'after' moves to Monday, which falls in the NEXT ISO week, so it gets the same occurrenceId as the following week's occurrence -> two distinct occurrences share one occurrenceId. For 'daily', the occurrenceId is literally formatDate(adjusted date); with weekend adjustment 'after', Saturday->Monday and Sunday->Monday collapse to the same scheduledDate AND the same occurrenceId as the genuine Monday occurrence -> three occurrences become three transactions on the same day with identical IDs. This breaks the merge de-dup in projectionMerger.ts (getKey uses occurrenceId): a single completed/stored transaction matches the wrong projection by occurrenceId, leaving a duplicate projected occurrence that is still counted in balances/forecasts; and identical proj_ IDs collide as React keys and over-count cash flow.
- Scenario: Weekly income, payday Sunday, weekendAdjustment 'after'. Occurrence Sun 2025-06-15 adjusts to Mon 2025-06-16 (ISO week 25); occurrence Sun 2025-06-22 stays/also resolves to ISO week 25. Both get occurrenceId sourceId_2025-W25. If the user marks the Jun-23 (second) occurrence complete, the stored completed transaction (occId W25) matches the FIRST projection in iteration order; the merger replaces Jun-16 with the completed record and re-emits Jun-23 as a still-'projected' transaction. Net: balance already had the completed amount applied AND the forecast still counts a projected occurrence for the same logical week -> the income is double-counted. Daily case: a daily $20 expense with 'after' adjustment over Sat/Sun/Mon yields three transactions all dated Monday with identical IDs, counting $60 on Monday instead of $20/day across the weekend.
- Suggested fix: Compute the occurrenceId from the UN-adjusted recurrence date (the logical period anchor), not the weekend-adjusted date. Pass the original date into generateOccurrenceId and apply adjustForWeekend only to the displayed scheduledDate, so the stable key is independent of weekend shifting.
- First-round verification: 3 votes, 1 refutes

### [F38] (critical/logic-error) Occurrence ID is computed from the weekend-ADJUSTED date, breaking ID stability and colliding across periods
- File: app/lib/logic/projectionEngine/incomeProjections.ts : 36-44 (incomeProjections); 55-63 (expenseProjections.ts); occurrenceIdGenerator.ts 50-101
- Why wrong: calculateOccurrences() returns dates that have ALREADY been weekend-adjusted (adjustForWeekend is applied inside the engine before the date is returned). incomeProjections/expenseProjections then pass that adjusted date into generateOccurrenceId. But generateOccurrenceId's own docstring states the ID 'represents the logical recurrence period ... so it remains stable even if the scheduled date shifts (weekend adjust ...)'. For monthly the ID is `${sourceId}_${year}-${month}` computed from target.getMonth(); for weekly it is the ISO week of target; for daily it is formatDate(target). When weekend adjustment shifts a date across a month/week boundary, the ID reflects the WRONG period and can equal the ID of the adjacent period's occurrence. The fix is to pass the pre-adjustment (logical) date to generateOccurrenceId, or to have calculateOccurrences return both the logical and adjusted dates so the ID is derived from the logical one.
- Scenario: Monthly rent, dayOfMonth=1, weekendAdjustment='before'. Jan 1 2025 is Wed -> emitted Jan 1, ID=rent_2025-01. Feb 1 2025 is Sat -> 'before' shifts to Jan 31 2025, and generateOccurrenceId(Jan 31) yields rent_2025-01. The February occurrence now collides with the January occurrence ID. In projectionMerger.ts the merge map keys on occurrenceId (getKey returns t.occurrenceId), so the two occurrences collapse to one entry -> February's rent disappears from the projection / an override saved for January is silently applied to February. Correct: February's ID must be rent_2025-02 regardless of the Friday shift. (Same mechanism: March 1 2025 Sat with 'before' -> Feb 28, ID rent_2025-02 instead of rent_2025-03.)
- Suggested fix: Derive the occurrence ID from the logical (un-weekend-adjusted) date. Either compute occurrenceId inside calculateOccurrences before calling adjustForWeekend and return {logicalDate, scheduledDate}, or do not apply weekend adjustment inside calculateOccurrences and instead apply it in transactionFactory after the ID is generated.
- First-round verification: 3 votes, 0 refutes
