# Cluster C1

Projection view-range parsed UTC vs local-built occurrence dates -> whole paydays dropped at month boundaries

Source files implicated:
- app/contexts/FinancialContext/utils/projectionMerger.ts

## Member findings (from first-round analysts)

### [F1] (critical/bug) Range boundary uses UTC-parsed dates compared against locally-built occurrence dates, dropping first/last-day occurrences depending on timezone
- File: app/contexts/FinancialContext/utils/projectionMerger.ts : 28-33
- Why wrong: viewDateRange.start/end are 'YYYY-MM-DD' strings. `new Date("YYYY-MM-DD")` parses as UTC midnight, but the occurrence calculator builds candidate dates with `new Date(year, month, day)` (LOCAL midnight) and with `parseDate` (dayjs LOCAL midnight). Because the two date-construction methods disagree by the UTC offset, the inclusive comparisons `date >= viewStartDate` and `date <= effectiveEnd` (occurrenceCalculator.ts) silently exclude legitimate occurrences. In positive-offset zones (e.g. Asia/Manila +8, most of Europe/Asia/Australia) `new Date('2026-06-01')` = local 08:00 on Jun 1, so an occurrence at local 00:00 on Jun 1 fails `date >= viewStartDate` and the 1st-of-month payment is dropped. In negative-offset zones (e.g. America/New_York -4) `new Date('2026-06-30')` = local 20:00 on Jun 29, so an occurrence at local 00:00 on Jun 30 fails `date <= effectiveEnd` and the last-day payment is dropped. The correct fix is to parse the view bounds with the same local parser (`parseDate`) and to compare against day-granular boundaries (e.g. end-of-day for the end bound), so boundaries are timezone-stable.
- Scenario: User in Manila (UTC+8) with salary scheduled monthly on the 1st, viewing June 2026. viewDateRange.start='2026-06-01'. `new Date('2026-06-01')` = Jun 1 08:00 local; the June salary occurrence is built as Jun 1 00:00 local; `occ >= viewStart` is false, so the June salary is omitted from the month's projections (verified via node: occ>=viewStart? false). Correct output: June salary appears on the 1st. Symmetrically, a New York user loses any payment due on the last day of the viewed month (verified: occ June30 <= viewEnd? false).
- Suggested fix: Parse the view window with the same local parser used for occurrences and make the end inclusive at day granularity, e.g. `parseDate(viewDateRange.start)` and `dayjs(parseDate(viewDateRange.end)).endOf('day').toDate()`, and/or compare occurrences by formatted YYYY-MM-DD string rather than by raw timestamp.
- First-round verification: 3 votes, 0 refutes

### [F9] (high/edge-case) View-range boundary parsed as UTC midnight while occurrence dates are local midnight, dropping (or adding) first/last-day occurrences in non-UTC timezones
- File: app/contexts/FinancialContext/utils/projectionMerger.ts : 28-33
- Why wrong: viewDateRange.start/end are 'YYYY-MM-DD' strings. new Date('YYYY-MM-DD') parses as UTC midnight. But occurrenceCalculator builds candidate dates with new Date(year, month, day) (local midnight) and with parseDate (dayjs, local), then compares date >= viewStartDate / date <= effectiveEnd. In any timezone east of UTC (positive offset, e.g. Asia/Manila UTC+8 which matches typical users of this app), local midnight of the first view day is 16:00 UTC of the PREVIOUS day, which is < the UTC-parsed viewStartDate, so the inequality date >= viewStartDate is false and the occurrence on the first day of the window is dropped. Symmetrically, the end boundary comparison can drop a last-day occurrence in UTC- zones or admit an out-of-range one. The codebase deliberately added parseDate/formatDate (dateUtils.ts) to avoid exactly this UTC-vs-local mismatch, but the merger bypasses it by calling new Date(string) directly.
- Scenario: Timezone Asia/Manila (UTC+8). viewDateRange.start = '2025-06-01' -> new Date('2025-06-01') = 2025-06-01T00:00Z. A monthly salary with dayOfMonth 1 generates new Date(2025,5,1) = 2025-05-31T16:00Z locally. The check date >= viewStartDate evaluates 2025-05-31T16:00Z >= 2025-06-01T00:00Z = false, so the June 1 paycheck is omitted from the June view entirely. Correct behavior: the June 1 occurrence falls within a window starting June 1 and must be included. The user sees a missing income on the first of the month and an understated month-opening balance.
- Suggested fix: Parse the view range with the same local-time helper used everywhere else: pass parseDate(viewDateRange.start) and parseDate(viewDateRange.end) (and ideally startOfDay/endOfDay) into generateProjections instead of new Date(string). Apply the same fix to useComputedFinancials.ts:21-22 which has the identical pattern.
- First-round verification: 3 votes, 0 refutes

### [F42] (high/bug) View-window bounds parsed as UTC (new Date("YYYY-MM-DD")) while occurrence dates are built in local time, dropping the first/last calendar day of the window in non-UTC timezones
- File: app/contexts/FinancialContext/utils/projectionMerger.ts : 28-33 (caller) feeding occurrenceCalculator.ts 30-44, 51, 73-74, 96-97, 120, 141, 161, 179
- Why wrong: The view bounds are produced with new Date("YYYY-MM-DD"), which JavaScript parses as UTC midnight, whereas the occurrence engine builds candidate dates with new Date(year, month, day) (LOCAL midnight) and parses start/end with dayjs (LOCAL). The engine then compares local-midnight occurrence dates against the UTC-derived bounds using >= viewStartDate and <= effectiveEnd. In any timezone west of UTC the view-end bound resolves to the previous local evening, so the last calendar day of the window is dropped; east of UTC the view-start bound resolves to the next local morning, dropping the first day. The dateUtils.parseDate helper exists precisely to avoid this UTC parsing, but the caller bypasses it; the engine's boundary comparisons therefore mix two time bases.
- Scenario: Timezone America/New_York (UTC-4 in summer). viewDateRange.end='2025-06-30' -> new Date('2025-06-30') = 2025-06-29 20:00 local. A monthly/daily occurrence on 2025-06-30 is built as 2025-06-30 00:00 local; 2025-06-30 00:00 <= 2025-06-29 20:00 is FALSE, so June 30 is dropped from the June calendar even though it is in range. In Asia/Tokyo (UTC+9), viewDateRange.start='2025-06-01' -> 2025-06-01 09:00 local, and an occurrence on 2025-06-01 00:00 local fails >= viewStartDate, dropping June 1. Correct: parse bounds with the same local parser (parseDate) used for occurrence dates, or compare on date-string (YYYY-MM-DD) equality rather than Date getTime.
- Suggested fix: Parse view bounds with parseDate(viewDateRange.start)/parseDate(viewDateRange.end) (dayjs local) in projectionMerger, or have calculateOccurrences normalize all bounds and candidate dates to local startOfDay before comparison; better still, compare on YYYY-MM-DD strings to be timezone-agnostic.
- First-round verification: 3 votes, 0 refutes
