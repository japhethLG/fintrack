# Cluster C6

dailyBalance opening balance: undoes ALL completed but re-applies only windowed; balanceLastUpdatedAt anchor ignored; past manual projected summed

Source files implicated:
- app/lib/logic/balanceCalculator/dailyBalance.ts

## Member findings (from first-round analysts)

### [F16] (critical/logic-error) Completed transactions dated before the view window are 'undone' from the opening balance but never re-applied, corrupting the entire visible balance
- File: app/lib/logic/balanceCalculator/dailyBalance.ts : 30-53
- Why wrong: currentBalance is an anchor that already reflects every completed transaction up to balanceLastUpdatedAt (adjustUserBalance adds the delta to currentBalance on each completion, see transactionActions.ts:113-114 and userActions.ts:81-98). To reconstruct daily balances, the code undoes the effect of ALL completed transactions (regardless of date) to get a 'before any transaction' opening balance, then re-applies each transaction day-by-day. But getDaysBetween only iterates from startDate (the view range, which useViewDateRange.ts defaults to 2 months back) through endDate. Any completed transaction whose date is BEFORE startDate gets undone from openingBalance yet is never re-applied because its day is outside the iterated range. The net effect of all such out-of-window completed transactions is permanently removed from the opening balance and therefore from every single day shown in the calendar. The correct anchor should be: opening balance at startDate = currentBalance minus only the net effect of completed transactions dated on/after startDate (i.e. reverse only the in-window completed transactions), or equivalently compute the balance as of startDate from a full history. balanceLastUpdatedAt is not consulted at all, so there is no anchoring as the spec/task requires.
- Scenario: Today is 2026-06-01, so useViewDateRange defaults to start=2026-04-01. A user has been active a year with 12 completed monthly salary deposits of 3000 each, all dated in 2025 (before the window). currentBalance = 36000 (all 12 already reflected). calculateDailyBalances undoes all 12 (openingBalance -= 36000 -> 0), but none of them fall on a day in 2026-04-01..2026-07-31, so none are re-added. Result: the window opening balance and every day's balance in the calendar are understated by 36000 — the calendar shows an opening/closing balance of 0 instead of the real 36000. With a single old completed expense of 1000, the entire window is instead overstated by 1000 (opening shows 6000 instead of 5000). The error equals the signed net of every completed transaction dated before startDate and grows without bound the longer the user uses the app.
- Suggested fix: Only reverse completed transactions that fall within (or after) the iterated date range. For example, when building openingBalance, skip transactions whose effective date (actualDate || scheduledDate) is < formatDate(startDate). Better: anchor explicitly on balanceLastUpdatedAt — treat currentBalance as the true balance as of that date and walk forward/backward from there, never undoing transactions dated on/before the anchor that startDate predates. The function should also receive balanceLastUpdatedAt (currently unused) to do this correctly.

### [F17] (medium/edge-case) Reconstructed 'today' balance does not equal currentBalance when a completed transaction has a future actualDate
- File: app/lib/logic/balanceCalculator/dailyBalance.ts : 31-45
- Why wrong: The opening-balance reconstruction undoes completed transactions unconditionally, and the day-grouping places each completed transaction's effect on its actualDate. When actualDate is in the future relative to today (e.g. the user completes/prepays a future-dated bill, which immediately mutates currentBalance via adjustUserBalance), the effect is removed from the opening balance and re-applied only on that future day. Consequently the closing balance for the current day (and every day between today and that future actualDate) does NOT equal currentBalance, even though currentBalance already includes that completed transaction. The displayed 'current' balance is therefore inconsistent with the stored currentBalance the rest of the app shows.
- Scenario: Today 2026-06-01, currentBalance = 5000 which already includes a completed expense of 500 the user marked complete with actualDate 2026-06-20. calculateDailyBalances undoes it (openingBalance becomes 5500) and re-applies the -500 only on 2026-06-20. The calendar's closing balance for 2026-06-01 shows 5500, but the real account/currentBalance is 5000. The number only 'catches up' to 5000 on 2026-06-20.
- Suggested fix: Decide on a single source of truth for completed transactions. Either anchor on balanceLastUpdatedAt and only reverse completed transactions dated after the anchor, or clamp completed transactions' effective date to min(actualDate, balanceLastUpdatedAt) for reconstruction so that currentBalance is always reproduced as of the anchor date.
- First-round verification: UNVERIFIED (verifier crashed)

### [F25] (critical/bug) Daily balance opening-balance undoes completed transactions dated OUTSIDE the view window without re-applying them, corrupting the cash-flow chart and balance-trend score
- File: app/lib/logic/balanceCalculator/dailyBalance.ts : 30-53
- Why wrong: The opening balance is derived by undoing EVERY completed transaction in the `transactions` array, with no date filter. But the running-balance loop only walks days from `startDate` to `endDate`, so it only RE-APPLIES completed transactions whose date falls inside [startDate, endDate]. Completed transactions dated before `startDate` (or after `endDate`) are subtracted from the opening balance but never added back, so the opening (and therefore every) balance in the window is off by the net of those out-of-range completed transactions. The merged `transactions` array does include such out-of-range stored/completed transactions: projectionMerger.ts (lines 71-84) unconditionally appends manual transactions and unmatched stored transactions regardless of date. The Dashboard CashFlowChart reads `dailyBalances.get(dateKey).closingBalance` (Dashboard.tsx line 124), so the entire 'Projected Cash Flow' Opening/Closing/Change figures inherit this error. The balance-trend health score also reads these closing balances and divides the slope by avgBalance (scoreCalculators.ts line 202), so a wrong offset distorts the normalized trend.
- Scenario: currentBalance = $1,000. There is one completed expense of $500 with actualDate 2026-05-20 (last month). User views Dashboard for June 1-30 (viewDateRange start = 2026-06-01). Opening balance is computed as 1000 + 500 = $1,500 (May expense added back) but the June loop never re-subtracts it, so the chart's opening balance shows $1,500 and every June closing balance is $500 too high. Correct opening balance for June 1 is $1,000 (the May expense already happened and is reflected in currentBalance).
- Suggested fix: Only undo completed transactions whose effective date is within (or after) the projection window when reconstructing the opening balance — e.g. undo completed transactions on/after startDate only, since currentBalance already reflects all completed transactions and the loop will re-apply those inside the window. Equivalently, compute openingBalance by undoing only the completed transactions that the day-loop will re-apply (date in [startDate,endDate]).

### [F47] (critical/logic-error) Completed transactions BEFORE the view-range start are undone from currentBalance but never re-applied, corrupting the entire running balance
- File: app/lib/logic/balanceCalculator/dailyBalance.ts : 30-53
- Why wrong: The opening balance is derived by subtracting/adding back EVERY completed transaction in the array (no date filter). Per computedBalance.ts, currentBalance = initialBalance + sum(all completed), so this 'undo' step yields openingBalance = initialBalance. The day loop (getDaysBetween) then re-applies transactions ONLY for dates within [startDate, endDate]. But subscribeToStoredTransactions (transactions.ts:347-356) fetches ALL stored transactions with NO date filtering, and the view range (useViewDateRange.ts:17-18) starts only ~2 months in the past. Any completed transaction dated before startDate is therefore undone from the opening balance but is NEVER re-added in the loop, because its date never appears in getDaysBetween. The result is that openingBalance (= initialBalance) is missing the net effect of all pre-range completed history, so every single day's opening/closing balance shown in the calendar is wrong by that amount.
- Scenario: User started tracking 2024-01-01 with initialBalance = 1000. Over the past year they completed income/expenses netting +4000, and currentBalance is correctly 5000. View range default starts 2026-04-01 (2 months before today 2026-06-01). All those completed transactions are dated before 2026-04-01. The undo loop computes openingBalance = 5000 - 4000 = 1000 (= initialBalance). The day loop from 2026-04-01 onward only re-applies transactions dated >= 2026-04-01. The day cell for today (2026-06-01) therefore shows a running balance anchored on 1000 instead of 5000 (it is short by the entire 4000 of pre-range net history). Correct behavior: the balance shown for today must equal currentBalance (5000); the engine should anchor the running balance to currentBalance at balanceLastUpdatedAt and only project transactions AFTER that anchor forward (and reverse transactions BEFORE it for past days), not blindly undo all completed history and replay only the in-range subset.
- Suggested fix: Anchor to the known truth instead of an unbounded undo: set the running balance for the anchor date (balanceLastUpdatedAt / today) directly to currentBalance, then walk forward applying only transactions dated after the anchor and walk backward reversing transactions dated on/after each prior day. Equivalently, seed openingBalance = initialBalance + sum(completed with date < startDate) so pre-range completed history is preserved, then replay only in-range transactions.
- First-round verification: 3 votes, 0 refutes

### [F48] (critical/correctness) balanceLastUpdatedAt anchor is completely ignored; past projected/pending transactions are applied as if they happened, desyncing today's balance from currentBalance
- File: app/lib/logic/balanceCalculator/dailyBalance.ts : 55-94
- Why wrong: currentBalance is, by design (computedBalance.ts + users.ts updateUserBalance), the actual bank balance as of balanceLastUpdatedAt and equals initialBalance + sum(completed). The function never reads balanceLastUpdatedAt. Because openingBalance reduces to initialBalance and the loop then adds back BOTH completed AND projected/pending transactions for every in-range day (the ternary falls through to projectedAmount for any non-completed, non-skipped status), the running balance at the anchor date does NOT reconcile to currentBalance whenever there exist past (date <= today) projected/pending transactions in range. Those are uncompleted bills/income that have NOT actually hit the bank, yet they are applied to the running balance for days at and after their date. So 'today' no longer shows currentBalance.
- Scenario: Today is 2026-06-01, currentBalance = 5000, initialBalance = 5000 (no completed history). There is one projected expense of 800 dated 2026-05-20 (a bill the user never marked complete and never paid) that sits inside the view range. Undo loop: no completed txns, openingBalance = 5000. Day loop reaches 2026-05-20 and subtracts the 800 projected expense, so today (2026-06-01) shows running balance 4200. But the user's real balance today is 5000 (the bill was never paid). The engine reports 4200, understating the balance by 800. Correct behavior: the running balance at balanceLastUpdatedAt must equal currentBalance; past uncompleted projections should not retroactively move the balance below the anchor. Only future transactions (after the anchor) should adjust the projected balance.
- Suggested fix: Use balanceLastUpdatedAt as a hard anchor: force runningBalance to currentBalance on that date regardless of in-range projections, and only let transactions dated strictly after the anchor change the projected forward balance. For days before the anchor, reconstruct historically (reverse completed actuals) rather than replaying projected amounts that may never have occurred.
- First-round verification: 3 votes, 0 refutes

### [F49] (high/edge-case) Manual 'projected' transactions in the past are not part of currentBalance yet are summed into the running balance (and double-counting once completed)
- File: app/lib/logic/balanceCalculator/dailyBalance.ts : 63-76
- Why wrong: computeBalanceFromTransactions (computedBalance.ts:22-31) — the declared source of truth for currentBalance — counts ONLY status === 'completed'. This daily calculator instead counts every status except 'skipped' (i.e., it also applies 'projected'/pending). For a fully consistent ledger this is acceptable for FUTURE projection, but combined with the undo-anchor that targets initialBalance, it means the two engines disagree about what affects the balance. A pending/projected transaction moves the daily-balance line but does not move currentBalance, so the calendar's running balance and the dashboard's currentBalance diverge for the same date. There is no reconciliation guaranteeing balances.get(today).closingBalance === currentBalance.
- Scenario: currentBalance = 2000 (no completed txns). A manual 'projected' income of 1000 is stored with scheduledDate 2026-05-15 (past). Settings page (computeBalanceFromTransactions) shows computed balance 2000 (projected ignored). Calendar day loop adds 1000 at 2026-05-15, so the running balance for today shows 3000. The two surfaces disagree by 1000 for the same 'now'. Correct behavior: define a single rule for what affects realized balance (completed only) versus projected balance, and ensure the day cell at the anchor reconciles to currentBalance.
- Suggested fix: Make the realized-vs-projected boundary explicit and consistent with computeBalanceFromTransactions: realized balance up to balanceLastUpdatedAt should use completed actuals only; from the anchor forward, project using projected amounts. Do not apply past projected/pending amounts to the realized running balance.
- First-round verification: 3 votes, 1 refutes
