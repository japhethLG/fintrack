### [F45] (medium/edge-case) Credit-card first payment date uses setDate(dueDate) with no month-length clamp, overflowing into the next month for short start months
- File: app/lib/logic/projectionEngine/creditProjections.ts : 31-46
- Why wrong: Line 35 does a raw firstPaymentDate.setDate(creditConfig.dueDate) without clamping to the number of days in the start month — unlike the later branch (lines 40-45) and the per-step loop (lines 72-77) which both use Math.min(dueDate, lastDayOfMonth). JavaScript's Date.setDate(31) on a 28/30-day month rolls over into the following month. This produces a first payment date in the wrong month, which then seeds the entire generated schedule (calculateDecliningMinimumPayoff / calculateCreditCardPayoff start from firstPaymentDate), shifting the whole projection.
- Scenario: rule.startDate = 2026-02-10, creditConfig.dueDate = 31. Line 34: firstPaymentDate = Feb 10 2026. Line 35: setDate(31) → February has 28 days, so it rolls to 2026-03-03. 2026-03-03 < 2026-02-10 is false, so the next-month branch is skipped and firstPaymentDate stays 2026-03-03. The first projected credit-card payment is dated March 3 instead of the intended February 28 (the due date clamped to the month). All subsequent monthly payments inherit this off-by-one-month / wrong-day origin.
- Suggested fix: Clamp on line 35 the same way the other branches do: firstPaymentDate.setDate(Math.min(creditConfig.dueDate, new Date(startDateParsed.getFullYear(), startDateParsed.getMonth() + 1, 0).getDate())).
- First-round verification: 3 votes, 0 refutes

### [F67] (high/logic-error) Scenario comparisons use a truncated baseline when current strategy never pays off (minimum-payment trap), producing negative savings and hiding genuinely beneficial scenarios
- File: app/lib/logic/creditCardCalculator/scenarioCalculator.ts : 20-85
- Why wrong: When the current payment strategy never pays off (payment <= monthly interest), the underlying schedule (calculateCreditCardPayoff / calculateDecliningMinimumPayoff) does not run to completion; it hits the `if (month > 12 && principal < 0.01) break;` guard and STOPS at month 13 with the balance essentially unchanged. So `currentSchedule.length` is 13 and `currentInterest` is only the interest accrued in those 13 months (e.g. 1300), NOT the true 'never pays off / infinite interest' baseline. Scenario savings are then computed as `currentInterest - scenarioInterest` and `currentMonths - scenarioMonths` against this tiny truncated baseline. A scenario that ACTUALLY pays the card off (e.g. Double Payment over 36 months with 2000 interest) gets `interestSavings = 1300 - 2000 = -700` and `timeSavingsMonths = 13 - 36 = -23`, i.e. it looks WORSE than the trap. The final `.filter(s => s.interestSavings > 0)` then discards it. The user who most needs help (stuck in a minimum-payment trap) is shown zero helpful scenarios, and any shown comparisons would have inverted (negative) savings. The baseline for a never-payoff strategy should be treated as Infinity (every escaping scenario has positive savings), or the comparison should be guarded for the non-terminating case.
- Scenario: CreditConfig: currentBalance=5000, apr=24 (monthly rate 2%), minimumPaymentMethod='percent_only', minimumPaymentPercent=2, minimumPaymentFloor=25, paymentStrategy='minimum'. Minimum payment = 5000*0.02 = 100 = monthly interest exactly, so principal=0 forever (true trap). calculateDecliningMinimumPayoff returns length 13, cumulativeInterest=1300. Double Payment scenario = 200/mo, which pays off in 36 months with totalInterest=2000.56. Code computes interestSavings = 1300 - 2000.56 = -700.56 and timeSavingsMonths = 13 - 36 = -23, so the filter `interestSavings > 0` removes it. Correct behavior: current strategy never pays off (infinite interest), so Double Payment SAVES infinite interest and 'never -> 36 months' of time and must be surfaced.
- Suggested fix: Detect the non-terminating baseline before computing savings. Determine `currentWillPayOff = currentSchedule.length>0 && currentSchedule[currentSchedule.length-1].remainingBalance < 0.01`. If false, set the baseline interest/months to Infinity so every paying-off scenario yields positive savings and a meaningful 'Never -> N months' time saving, and do not filter those out. Only apply the `interestSavings > 0` filter when the current strategy itself pays off.

### [F68] (medium/correctness) full_balance payment strategy accrues a month of interest and leaves a residual, taking two months to clear instead of one and ignoring the grace period
- File: app/lib/logic/creditCardCalculator/payoffCalculator.ts : 30-56
- Why wrong: For paymentStrategy='full_balance', getEffectivePayment returns config.currentBalance (the bare balance, not balance+interest). calculateCreditCardPayoff accrues a full month of interest FIRST (`interest = balance * monthlyRate`), then since payment (= balance) is less than balance+interest, principal = balance - interest, leaving a residual equal to one month's interest. The card therefore takes a SECOND month to clear and reports nonzero totalInterest. In reality, paying the full statement balance by the due date incurs no interest (grace period) for purchases, and even on a true revolving balance, 'pay the full balance' should clear it in a single payment. The model overstates both payoff time (2 months vs 1) and total interest for the full_balance strategy.
- Scenario: currentBalance=5000, apr=24, paymentStrategy='full_balance'. Effective payment = 5000. Month 1: interest=100, principal=4900, remainingBalance=100. Month 2: pays remaining 100+2 interest. Result: monthsToPayoff=2, totalInterestToPay=102. Expected for 'pay full balance': monthsToPayoff=1, totalInterest=0 (grace) or at most the full balance clears in one payment with remainingBalance=0.
- Suggested fix: For full_balance, the payment should equal balance + accrued interest (or interest should not be accrued at all for the full-balance grace-period case). Either set the effective payment to currentBalance + monthlyInterest, or special-case full_balance so the schedule clears to zero in month 1 with totalInterest reflecting the grace-period semantics.

### [F69] (low/correctness) Monthly interest uses nominal APR/12 rather than a daily periodic rate times days in the cycle
- File: app/lib/logic/creditCardCalculator/payoffCalculator.ts : 25-31
- Why wrong: Real-world credit card interest is typically computed as a daily periodic rate (APR/365) applied to the average daily balance and multiplied by the number of days in the billing cycle, which compounds and produces slightly more interest than the simple nominal APR/12 used here (and used identically in paymentCalculator.ts line 13 and summaryCalculator.ts line 23). APR/12 is a widely accepted approximation, so this is informational rather than a hard bug, but it systematically under-states monthly interest for cards that quote APR as a daily-rate product, and assumes uniform 1/12-of-a-year months.
- Scenario: balance=5000, apr=24. Code computes monthly interest = 5000*(0.24/12) = 100.00. A daily-periodic-rate model over a 30-day cycle gives 5000*(0.24/365)*30 = 98.63 (simple) or 99.58 (compounded daily). Over a long payoff this difference accumulates and the reported totalInterestToPay deviates by a small but consistent margin.
- Suggested fix: If matching issuer statements is a goal, compute interest as balance * (apr/100/365) * daysInCycle (and document the choice). Otherwise document explicitly that APR/12 nominal monthly compounding is the intended convention so callers do not expect statement-exact figures.

### [F70] (low/structure) Unused currentTotal computation in scenario calculator (dead variable)
- File: app/lib/logic/creditCardCalculator/scenarioCalculator.ts : 22-22
- Why wrong: currentTotal is computed by summing all payments in the current schedule but is never referenced anywhere in calculatePayoffScenarios. It is dead code. More importantly its presence suggests an intended 'total amount paid' savings comparison (currentTotal - scenario.totalAmount) that was never wired up, so the scenarios only ever compare interest and time, never total outlay. This compounds the truncated-baseline problem in the trap case (the total a user would pay under a never-ending minimum is not surfaced).
- Scenario: Any call to calculatePayoffScenarios computes currentTotal then discards it; no scenario output uses it, and there is no totalAmountSavings field in PayoffScenario.
- Suggested fix: Either remove the unused variable, or use it to populate a total-cost comparison (e.g. a totalSavings = currentTotal - scenario.totalAmount field), guarding for the non-terminating baseline as described in the trap finding.
