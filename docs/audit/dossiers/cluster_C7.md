# Cluster C7

runway/nextCrunch: double-count completed (currentBalance already includes them); ignore overdue; crunch-only-on-expense-day; infinite-runway return

Source files implicated:
- app/lib/logic/balanceCalculator/runway.ts

## Member findings (from first-round analysts)

### [F26] (medium/correctness) getRunway (Cash Runway metric) double-counts future completed transactions because it does not exclude completed status, unlike the runway health-score
- File: app/lib/logic/balanceCalculator/runway.ts : 32-46
- Why wrong: getRunway starts from currentBalance (which already includes the effect of all completed transactions) and then walks forward applying every non-skipped transaction, INCLUDING completed ones. The parallel health-score runway calculator (scoreCalculators.ts line 36) correctly filters `t.status !== "completed"` precisely to avoid re-applying already-settled transactions. Because currentBalance already reflects completed transactions, any completed transaction whose actualDate/scheduledDate is today or in the future will be applied a second time, distorting the projected balance walk and thus the runway days / run-out date shown in the Forecast MetricsGrid (Forecast.tsx line 273). getNextCrunch (lines 82-101) has the identical omission.
- Scenario: currentBalance already includes a completed income of $1,000 whose actualDate is today (2026-06-01). getRunway iterates day 0, finds that completed income, and adds $1,000 again — projecting the balance $1,000 too high and overstating runway. The runway health-score, which excludes completed, would not. Correct: future projection should only apply not-yet-settled (projected) transactions since currentBalance already embeds completed ones.
- Suggested fix: Add `&& t.status !== "completed"` to the day-transaction filters in both getRunway and getNextCrunch, matching calculateRunwayScore, so completed transactions are not re-applied on top of currentBalance.

### [F51] (medium/logic-error) getNextCrunch only reports a crunch when the negative balance occurs on a day that also has an expense, missing crunches caused by carried-over deficits
- File: app/lib/logic/balanceCalculator/runway.ts : 101-108
- Why wrong: The crunch detection requires dayExpenses > 0 on the same day the balance is negative. If the balance is already negative from a prior day's expense and a later day has no expense (or only income that fails to bring it positive), the negative state is not reported on those days. More subtly, a day whose only transactions are expenses that push the balance negative is caught, but a day where the balance was driven negative earlier and stays negative is never flagged at its true onset if the onset day's net was driven by a non-expense path. getRunway (lines 48-52) uses the correct condition (balance < 0 with no expense gate), so the two functions disagree about when funds run out.
- Scenario: currentBalance = 100. Day 1: expense 150 -> balance -50, dayExpenses>0 so crunch correctly reported. But consider currentBalance = 100, Day 1 expense 80 -> balance 20 (no crunch), Day 2 no transactions, Day 3 income 0 / a refund reversal modeled as negative income... balance stays 20. Now consider Day 5 has an expense 0-amount edge or a day where balance first goes negative due to accumulated small expenses on a day with dayExpenses==0 (e.g., only a skipped/income line): such a negative onset is skipped. getRunway would flag it; getNextCrunch would not, so the dashboard's 'next crunch' can be null while runway says funds are already exhausted.
- Suggested fix: Drop the 'dayExpenses > 0' gate and report the first day balance < 0 (matching getRunway), or track the running minimum and report the first date the cumulative balance crosses below zero regardless of that day's expense composition.
- First-round verification: UNVERIFIED (verifier crashed)

### [F52] (critical/logic-error) getRunway double-counts completed transactions because currentBalance already includes them
- File: app/lib/logic/balanceCalculator/runway.ts : 20-46
- Why wrong: The seed `currentBalance` (passed as `userProfile.currentBalance` at Forecast.tsx:272) ALREADY reflects every completed transaction: `completeTransaction` calls `adjustUserBalance(userId, delta)` (transactions.ts:178-179), and `dailyBalance.ts:27-40` explicitly documents that currentBalance 'already includes completed transactions' and must be 'undone' before projecting forward. The runway loop, however, does NOT exclude completed transactions — its only filter is `t.status !== "skipped"`. For any completed transaction whose effective date (`actualDate || scheduledDate`) is today (i=0) or a future day inside the window, the loop re-applies the amount on top of an already-adjusted balance, double-counting it. Correct behavior: the forward simulation must start from a balance that excludes completed transactions (undo them like dailyBalance does) OR skip completed transactions in the loop, since their effect is baked into the seed balance.
- Scenario: currentBalance = 100 (already includes a $200 grocery bill completed TODAY, so before the bill the user had 300). Today the merged transactions contain that completed expense (status=completed, actualDate=today, actualAmount=200). getRunway(100, txns): i=0, dateKey=today matches the completed expense, so balance = 100 - 200 = -100. It reports runOutDate=today, days=0, screaming the user is already broke. Correct: the $200 is already in the 100 balance, so today's closing balance should remain 100 and runway should not flag today at all.
- Suggested fix: Before the loop, compute a forward-start balance that undoes completed transactions (mirror dailyBalance.ts), or in the per-day loop skip `t.status === "completed"` entirely so only projected/pending items move the balance. Pick one consistently so completed effects are counted exactly once.
- First-round verification: UNVERIFIED (verifier crashed)

### [F53] (high/logic-error) getNextCrunch double-counts completed transactions (same root cause as getRunway)
- File: app/lib/logic/balanceCalculator/runway.ts : 76-108
- Why wrong: getNextCrunch seeds `balance = currentBalance` (Forecast.tsx:274 passes userProfile.currentBalance, which already includes completed transactions) and then re-applies every non-skipped transaction including completed ones. Any transaction completed today or with a future effective date is added a second time, producing a spurious crunch (or wrong shortfall magnitude). The crunch date/shortfall shown to the user is therefore incorrect whenever completed transactions fall on/after `today` in the merged set.
- Scenario: currentBalance = 500 already includes a $500 rent payment completed today (status=completed, actualDate=today). getNextCrunch(500, txns): i=0 re-applies the completed $500 expense, balance = 0; if any further bill exists it now triggers a false crunch. With currentBalance=400 already including the completed $500 (pre-payment balance 900), i=0 gives 400-500 = -100 with dayExpenses>0, so it falsely reports a crunch TODAY with shortfall 100. Correct: the rent is already deducted, balance stays 400, no crunch today.
- Suggested fix: Exclude completed transactions from the per-day loop (their impact is already in currentBalance), or undo completed transactions before seeding the running balance — matching whatever fix is applied in getRunway.

### [F54] (medium/edge-case) Runway/crunch ignore overdue projected (unpaid past-due) transactions, overstating runway
- File: app/lib/logic/balanceCalculator/runway.ts : 27-31
- Why wrong: Both getRunway and getNextCrunch only iterate days from `today` forward (i starts at 0). A still-projected (unpaid) transaction whose scheduledDate is in the PAST is never matched by `txDate === dateKey` for any future day, so its outflow is silently dropped. Because it is not completed, it is also absent from currentBalance. The result: a real, still-owed past-due bill disappears from the runway/crunch entirely, making runway look longer and hiding an existing shortfall. Correct behavior: overdue unpaid (projected) outflows should be applied up-front (e.g., folded into the starting balance on day 0) so they are not lost.
- Scenario: currentBalance = 300. A projected $400 utility bill scheduled yesterday is still unpaid (status=projected, scheduledDate=yesterday) and present in the merged transactions. getRunway only checks dates from today onward, so the $400 is never subtracted; runway reports the user is solvent (300, no run-out). Correct: the user actually owes 400 against 300 and is already in shortfall.
- Suggested fix: Before the forward loop, subtract/add any non-skipped, non-completed transactions whose effective date < today into the starting balance (treat overdue projected items as due now), then iterate forward from today.
- First-round verification: UNVERIFIED (verifier crashed)

### [F57] (low/structure) getRunway returns days=maxDays for net-positive (infinite) runway, mismatching the UI's hardcoded '90+ days'
- File: app/lib/logic/balanceCalculator/runway.ts : 15-58
- Why wrong: When the balance never goes negative within the window the function returns days = maxDays (defaulting to 365) and runOutDate = null. The Forecast caller (Forecast.tsx:273) invokes getRunway with the default maxDays=365, but MetricsGrid.tsx:74 renders the no-run-out case as the literal string '90+ days'. The numeric `days` value (365) is silently discarded and a hardcoded '90+' label is shown that does not correspond to the 365-day horizon actually simulated. This is a structural/labeling inconsistency rather than a math error (the run-out detection itself is correct), but the displayed horizon is wrong/misleading.
- Scenario: User is strongly net-positive over the next year. getRunway returns {days:365, runOutDate:null}. UI shows 'Cash Runway: 90+ days' even though the engine actually verified solvency for 365 days. A different caller that does read `days` would get 365 for an effectively infinite runway, which is also semantically odd (not Infinity, not the literal 90).
- Suggested fix: Align the horizon: either pass maxDays=90 from the caller and keep the '90+' label, or have the UI derive the label from the actual maxDays / runway.days, and represent infinite runway with a clear sentinel (e.g., null days or Infinity) rather than the literal maxDays count.
