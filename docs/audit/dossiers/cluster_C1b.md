# Cluster C1b

Pervasive new Date("YYYY-MM-DD")/toISOString UTC date-key off-by-ones in other modules

Source files implicated:
- app/contexts/FinancialContext/hooks/useComputedFinancials.ts
- app/lib/utils/frequencyUtils.ts

## Member findings (from first-round analysts)

### [F18] (medium/correctness) View-range boundaries are computed in UTC but the day grid is formatted in local time, shifting the calendar by a day for sub-UTC timezones
- File: app/contexts/FinancialContext/hooks/useComputedFinancials.ts : 18-24
- Why wrong: viewDateRange.start/end are produced in useViewDateRange.ts via startDate.toISOString().split('T')[0], i.e. UTC date strings. Here they are passed to new Date(viewDateRange.start), which parses a bare 'YYYY-MM-DD' as UTC midnight. But inside calculateDailyBalances the day grid is generated with getDaysBetween + formatDate, and formatDate uses dayjs(date).format('YYYY-MM-DD') in LOCAL time. Transaction scheduledDate strings are also produced with the same LOCAL formatDate (transactionFactory.ts:43). For any timezone behind UTC, new Date('2026-04-01') is local 2026-03-31, so the first generated dateKey is '2026-03-31' and every dateKey is shifted one day earlier than intended. This both starts the window a day early and, more importantly, can misalign the per-day grouping boundaries relative to the locally-formatted transaction dates, so a transaction can land in the wrong day bucket / day balances are offset by one day.
- Scenario: User in America/Los_Angeles (UTC-7). useViewDateRange yields start='2026-04-01' (UTC). new Date('2026-04-01') evaluates to local Mar 31 2026 17:00. getDaysBetween/formatDate therefore emit the first dateKey '2026-03-31' and shift the whole grid by one day, while projected transactions are keyed by local formatDate. The calendar's opening day and balance alignment are off by one day for all sub-UTC users.
- Suggested fix: Parse the range strings with the same local parser used everywhere else, e.g. parseDate(viewDateRange.start)/parseDate(viewDateRange.end) (dayjs local) instead of new Date(...), and make useViewDateRange emit dates via the local formatDate helper rather than toISOString(). Keep one consistent timezone convention for all date string production and parsing.

### [F50] (medium/bug) prorateToDateRange and getBillCoverageReport parse YYYY-MM-DD with new Date(), risking UTC off-by-one day shifts that dateUtils.parseDate was created to avoid
- File: app/lib/utils/frequencyUtils.ts : 49-53
- Why wrong: dateUtils.ts:12-14 documents that new Date('YYYY-MM-DD') parses as UTC midnight, causing local-time off-by-one bugs, and provides parseDate() to avoid it. prorateToDateRange ignores that helper and calls new Date(startDate)/new Date(endDate) directly. In timezones west of UTC, both parse to the prior local day, and although both shift equally the diff is usually fine, but combined with Math.ceil on a value that should be an exact integer it is fragile; more importantly the same anti-pattern in billCoverage.ts:59 (parseDate is used there, good) versus useComputedFinancials passing new Date(viewDateRange.start) (index/hook) means range endpoints can land on the wrong local day. The proration over a 30-day month also produces non-integer day counts that misstate prorated totals.
- Scenario: In UTC+8, prorating a monthly amount of 3000 over startDate '2026-06-01' to endDate '2026-06-30': new Date('2026-06-01') = 2026-05-31T16:00 local, new Date('2026-06-30') = 2026-06-29T16:00 local; getTime diff = 29 days exactly, +1 = 30, fine here, but for ranges crossing a DST or when only one endpoint is affected the Math.ceil can yield 31 instead of 30, prorating 3100 instead of 3000. Correct behavior: use parseDate() (local) consistently for both endpoints so the day count is deterministic.
- Suggested fix: Replace new Date(startDate)/new Date(endDate) with parseDate(startDate)/parseDate(endDate) from dateUtils, and compute day spans via dayjs diff to avoid Math.ceil rounding artifacts.

### [F74] (medium/correctness) Chart bucketing/labels use new Date("YYYY-MM-DD") (UTC) so daily/weekly/monthly buckets shift by a day/month in negative-UTC timezones
- File: app/lib/logic/healthScore/chartData.ts : 42-54
- Why wrong: `new Date("2026-06-15")` parses as UTC midnight, but `getDate()`, `getDay()`, `getMonth()`, and `formatDate()` (dayjs, local) read it in local time. In any timezone behind UTC (e.g. US), the parsed instant is the evening of the PREVIOUS day, so the day/week/month derived from it is off by one. The rest of the codebase deliberately provides `parseDate()` (dayjs local parse) to avoid exactly this; chartData ignores it. Both the bucket assignment and the rendered labels are affected. Verified: in America/New_York, daily bucketKey for scheduledDate '2026-06-15' becomes '2026-06-14'; monthly label for bucket key '2026-06' renders as 'May 2026' and '2026-01' renders as 'Dec 2025' (see lines 73-82). This silently misattributes income/expense totals to the wrong day, week, and month, including pushing month-boundary transactions into the adjacent month.
- Scenario: User in EST has a $2000 paycheck on '2026-06-15'. Daily chart plots it under 'Jun 14'. With monthly bucketing, a transaction on '2026-06-01' (UTC-parsed to May 31 local) is bucketed under '2026-05' and a June bucket renders its label as 'May 2026'. Correct: all should map to June 15 / June.
- Suggested fix: Replace `new Date(t.actualDate || t.scheduledDate)` with `parseDate(...)` from dateUtils, and in the result mapping replace `new Date(date)` with `parseDate(date)` (for the 'YYYY-MM' key, parse as `parseDate(date + '-01')`). This keeps all date math local and consistent with the storage convention.
- First-round verification: UNVERIFIED (verifier crashed)

### [F78] (high/bug) calculateForecast uses toISOString() for date keys, producing off-by-one dates in positive-UTC-offset timezones (inconsistent with the projection engine's local formatDate keys)
- File: app/lib/logic/forecasting/forecastCalculator.ts : 26-44, 60
- Why wrong: Both the `todayStr` filter cutoff and the per-day loop key `dateStr` are derived with `Date.prototype.toISOString()`, which formats in UTC. Everywhere else in this codebase, date keys are produced with `formatDate` (dayjs, local time) — `createProjectedTransaction` sets `scheduledDate = formatDate(date)` (transactionFactory.ts:43), and the sibling balance/runway functions use `formatDate`/`addDays` (dailyBalance.ts:56, runway.ts:29). When the runtime timezone has a positive UTC offset (e.g. Asia/Manila UTC+8, which matches the project's user) and `startDate` is at local midnight (e.g. `dayjs().startOf('day')` or `new Date(y,m,d)`), `toISOString()` rolls the date BACKWARD by one day. So a local date of 2026-06-01 yields a key of 2026-05-31. This corrupts both the filter boundary and the day-bucketing: the day-0 forecast point is labeled with a past date, and transactions land in the wrong day bucket (off by one). Transaction matching `transactionsByDate[dateStr]` uses the projection engine's local-formatted scheduledDate keys, so the two key spaces disagree.
- Scenario: Runtime TZ = Asia/Manila (UTC+8). User has currentBalance and a projected income of 50000 with scheduledDate '2026-06-01'. Caller passes startDate = local midnight 2026-06-01 (verified: `new Date(2026,5,1,0,0,0).toISOString().split('T')[0]` returns '2026-05-31'). Result: todayStr = '2026-05-31'; the loop produces keys ['2026-05-31','2026-06-01','2026-06-02',...]. The forecast[0] point is dated '2026-05-31' (a day that should not exist in a forecast starting today), and the 2026-06-01 income lands on loop index 1 (forecast[1]) instead of index 0. Correct behavior (using local formatDate, as the rest of the engine does): forecast[0] dated '2026-06-01' with the income applied on day 0. Every forecast point is mis-dated by one day for this entire class of users.
- Suggested fix: Replace `startDate.toISOString().split("T")[0]` and `currentDate.toISOString().split("T")[0]` with `formatDate(...)` from app/lib/utils/dateUtils, and replace the `currentDate.setDate(currentDate.getDate()+1)` mutation with `addDays(...)` (or `dayjs(startDate).add(i,'day')`), matching dailyBalance.ts and runway.ts. This makes the forecast's date keys consistent with the projection engine's local scheduledDate keys.
- First-round verification: UNVERIFIED (verifier crashed)

### [F75] (medium/edge-case) Period comparison drops one boundary day (previous window ends a day early) in negative-UTC timezones
- File: app/components/pages/dashboard/components/PeriodComparison.tsx : 24-33
- Why wrong: `new Date(dateRange.start)` parses the YYYY-MM-DD string as UTC midnight, but `formatDate` (dayjs) renders in local time. Subtracting a fixed 24h and reformatting in a behind-UTC timezone yields a prevEnd that is two calendar days before `start` instead of one, leaving the day immediately before `start` in neither the current window (it starts at `start`) nor the previous window. This is the same UTC-parse vs local-format mismatch as the chart bug. The fix is to do the arithmetic with the local date helpers (parseDate/addDays) rather than raw new Date()/getTime().
- Scenario: Current range = 2026-06-01..2026-06-30. In America/New_York the code computes prevStart=2026-05-01, prevEnd=2026-05-30. The day 2026-05-31 is excluded from both windows, so any income/expense on May 31 is silently omitted from the previous-period comparison totals, distorting the percent-change figures. In a UTC/positive-offset timezone the same code yields the correct prevEnd=2026-05-31.
- Suggested fix: Compute previous-period bounds with the local helpers, e.g. `const startD = parseDate(dateRange.start); const prevEnd = addDays(startD, -1); const dayCount = getDaysBetween(parseDate(dateRange.start), parseDate(dateRange.end)).length; const prevStart = addDays(prevEnd, -(dayCount - 1));` so windows are contiguous regardless of timezone.
- First-round verification: UNVERIFIED (verifier crashed)
