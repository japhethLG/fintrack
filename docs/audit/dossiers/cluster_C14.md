# Cluster C14

Manual/projected transaction state: editing type income<->expense skips balance adjust; revert leaves stale actual; edit overwrites projectedAmount; completion ignores overrides

Source files implicated:
- app/contexts/FinancialContext/actions/transactionActions.ts
- app/components/pages/dashboard/components/ProjectedVsActualWidget.tsx
- app/components/pages/transactions/components/ManualTransactionForm/formHelpers.ts

## Member findings (from first-round analysts)

### [F10] (medium/correctness) Completing a projected transaction stores base source.amount and computes no variance, ignoring occurrence override amount and loan/installment per-payment amounts
- File: app/contexts/FinancialContext/actions/transactionActions.ts : 89-110
- Why wrong: When a projected (proj_) transaction is completed, this action writes projectedAmount: source.amount directly. It never reads source.occurrenceOverrides[occurrenceId]?.amount, even though createProjectedTransaction (transactionFactory.ts:37-42) used override?.amount as the displayed projected amount; it also ignores the per-occurrence amount that loan/credit/installment projections compute (step.payment / installmentAmount, attached via paymentBreakdown). Furthermore, addTransaction (firestore/transactions.ts:35-49) does NOT compute the variance field, whereas the stored-transaction path completeTransaction (line 166) sets variance = actualAmount - projectedAmount. So a completed projection is persisted with the wrong projectedAmount and with no variance at all, corrupting variance/actual-vs-projected reporting and any logic keyed on projectedAmount for that record.
- Scenario: User sets an occurrence override amount of $1,200 on a monthly rent rule whose base amount is $1,000 (e.g., a one-month rent increase). The calendar shows the projected occurrence as $1,200. The user marks it complete with actualAmount $1,200. The stored transaction records projectedAmount $1,000 (base) and no variance. The variance report later computes/treats projected as $1,000, showing a spurious +$200 over-budget variance for that period instead of $0. Same issue for a loan: a projection showing the amortized EMI's principal+interest is completed but stored with the rule's base amount and an empty paymentBreakdown.
- Suggested fix: Resolve the effective projected amount the same way the projection did: const override = source.occurrenceOverrides?.[occurrenceId]; const projected = override?.amount ?? perOccurrencePaymentAmount ?? source.amount; store that as projectedAmount, carry over paymentBreakdown for loan/credit/installment occurrences, and compute variance = data.actualAmount - projected so completed projections match the completeTransaction path.
- First-round verification: 3 votes, 0 refutes

### [F11] (high/logic-error) Override-adjusted projected amount is lost on completion, corrupting the projected-vs-actual variance metric
- File: app/components/pages/dashboard/components/ProjectedVsActualWidget.tsx : 44-56
- Why wrong: The widget reads the 'projected' figure straight from t.projectedAmount. For a still-projected occurrence this is correctly override-aware (createProjectedTransaction sets projectedAmount = override?.amount ?? source.amount). But when that same occurrence is completed, markTransactionCompleteAction (app/contexts/FinancialContext/actions/transactionActions.ts line 95) hard-codes 'projectedAmount: source.amount', discarding any per-occurrence override amount that was actually being projected. Because the merger replaces the projection with this stored transaction (matched by occurrenceId), the projected baseline the widget sums silently changes the moment the user marks the occurrence complete. Variance ('% collected' / '% spent') should compare actual against the amount that was projected for that occurrence; instead it compares against source.amount.
- Scenario: Monthly rent rule with source.amount = 1000. This month the user adjusted the projected amount via an occurrence override to 1200 (a known higher month). Before completion the widget shows Expenses 0 / 1200 (0% spent). The user pays exactly 1200 and marks it complete. The stored transaction is written with projectedAmount = 1000 (source.amount) and actualAmount = 1200. The widget now shows Expenses 1200 / 1000 = 120% spent and flips the bar to the red 'over budget' color, even though the user paid exactly what was projected (variance should be 0). Correct output: projected 1200, actual 1200, 100%.
- Suggested fix: Preserve the actually-projected amount on completion. In markTransactionCompleteAction use the override-aware projected amount (e.g. carry the projection's projectedAmount through the projection ID / lookup, or read override?.amount ?? source.amount) instead of always writing source.amount, so the widget's projectedAmount reflects what was projected for that occurrence.

### [F34] (critical/logic-error) Editing a completed manual transaction's TYPE (income↔expense) does not adjust the balance
- File: app/contexts/FinancialContext/actions/transactionActions.ts : 301-326
- Why wrong: updateManualTransactionAction computes every balance delta using existing.type (the OLD type) and never accounts for a change of type in `updates.type`. The ManualTransactionForm allows the Type select to be edited even when editing an existing completed transaction (app/.../ManualTransactionForm/index.tsx lines 108-113; the category reset is gated by !isEditing but the type field itself is never disabled). When a completed transaction's type flips, the original balance impact (e.g. +amount for income) must be reversed AND the new impact (e.g. -amount for expense) applied. Because both old and new deltas are computed with existing.type, the new sign is wrong. Worst case: if the amount is unchanged, oldAmount === newAmount so NO branch fires at all and the balance is not touched, even though the correct net change is 2*amount. The balance is maintained incrementally via adjustUserBalance (computeBalanceFromTransactions / syncComputedBalance only run on a manual reconcile in Settings), so the user's displayed currentBalance stays wrong until they manually reconcile.
- Scenario: User has currentBalance = 1000. They add a completed manual INCOME of 100 (balance becomes 1100). They then edit that transaction, change Type from Income to Expense, keep amount = 100, keep status Completed, Save. Correct result: balance should drop by 200 to 900 (reverse +100, apply -100). Actual result: oldAmount (100) === newAmount (100) so the `oldAmount !== newAmount` branch is skipped and no adjustUserBalance call happens; balance stays 1100 — off by 200. If instead the amount were also changed to 120, the code applies adjustmentDelta = newDelta - oldDelta = (+120) - (+100) = +20 using the wrong (income) sign, so balance becomes 1120 instead of the correct 880 — off by 240.
- Suggested fix: Compute the old impact using existing.type and the new impact using (updates.type ?? existing.type), then apply the net difference whenever the transaction is/was completed. e.g. const oldType = existing.type; const newType = updates.type ?? existing.type; const oldImpact = wasCompleted ? (oldType === 'income' ? oldAmount : -oldAmount) : 0; const newImpact = nowCompleted ? (newType === 'income' ? newAmount : -newAmount) : 0; if (oldImpact !== newImpact) await adjustUserBalance(userId, newImpact - oldImpact). Alternatively disable the Type field when editing an existing transaction.

### [F35] (medium/bug) Reverting/skipping a completed manual transaction leaves stale actualAmount/actualDate in Firestore
- File: app/contexts/FinancialContext/actions/transactionActions.ts : 309-326
- Why wrong: When the TransactionModal reverts a manual transaction (index.tsx lines 96-102) it sends updates = { status: 'projected', actualAmount: undefined, actualDate: undefined }. updateTransaction runs the payload through removeUndefined (app/lib/firebase/firestore/utils.ts), which STRIPS keys whose value is undefined rather than clearing them. Therefore the previously stored actualAmount and actualDate are NOT removed — the document keeps a status of 'projected'/'skipped' while still carrying a stale actualAmount and actualDate. The live currentBalance is correctly reversed via adjustUserBalance, so this is not a balance bug, but the persisted record is now internally inconsistent. The stale actualDate also leaks into downstream logic: TransactionsManager sorts by `a.actualDate || a.scheduledDate` and the reschedule fix uses `existing.status === 'completed' || existing.actualDate` (line 264) to decide whether to move actualDate, so a reverted-to-projected transaction is still treated as if it had an actual date.
- Scenario: Manual expense projected=100 is completed with actualAmount=120 on actualDate=2026-05-10 (balance -120). User opens it and chooses Revert (status→projected). After save the document is { status:'projected', projectedAmount:100, actualAmount:120, actualDate:'2026-05-10' }. Expected: actualAmount and actualDate cleared. The transaction now sorts by 2026-05-10 (its old actual date) instead of its scheduledDate, and a later drag-reschedule would overwrite actualDate even though the item is projected.
- Suggested fix: Explicitly persist nulls (or use Firestore deleteField()) when clearing fields, instead of relying on undefined which removeUndefined drops. e.g. on revert/skip set actualAmount: null, actualDate: null, variance: null and ensure updateTransaction/removeUndefined preserves nulls (or special-cases field deletion).

### [F36] (medium/correctness) Editing a completed manual transaction overwrites projectedAmount with the actual amount, destroying variance
- File: app/components/pages/transactions/components/ManualTransactionForm/formHelpers.ts : 33,80-93
- Why wrong: The edit form has a single 'amount' field. getDefaultValues prefills it from actualAmount ?? projectedAmount, and transformToTransactionData writes that single value into BOTH projectedAmount and actualAmount. So editing a completed manual transaction that had a variance (projected ≠ actual) collapses the two values to be equal, permanently erasing the projected/actual distinction. The variance report (app/lib/logic/balanceCalculator/variance.ts) recomputes variance as actual - projected from these stored fields, so after any edit the reported variance for that transaction silently becomes 0. Also note actualDate is forced to scheduledDate on every completed edit, discarding any previously captured actualDate that differed from the scheduled date.
- Scenario: Manual expense created projected=100, later completed with actualAmount=130 (variance +30). User edits the transaction only to fix a typo in the name and saves. transformToTransactionData writes projectedAmount=130, actualAmount=130. The variance report that previously showed a +30 overspend for this item now shows 0, understating projected-vs-actual analysis. If the actual purchase happened on 2026-05-20 but scheduledDate is 2026-05-15, the edit also resets actualDate to 2026-05-15.
- Suggested fix: Either preserve editData.projectedAmount separately (don't overwrite it from the single amount field on edit), or give the edit form distinct projected and actual fields. At minimum, when status is unchanged and already completed, keep the existing projectedAmount and only update actualAmount; preserve the existing actualDate unless the user explicitly changed it.

### [F37] (medium/correctness) Completing a projected occurrence ignores per-occurrence amount overrides for stored projectedAmount
- File: app/contexts/FinancialContext/actions/transactionActions.ts : 88-110
- Why wrong: When marking a projected (proj_*) occurrence complete, projectedAmount is hard-coded to source.amount (the rule's base amount). But the projection that the user saw may have a different amount: createProjectedTransaction (app/lib/logic/projectionEngine/transactionFactory.ts line 37-41) uses override?.amount ?? paymentBreakdown total ?? source.amount. So when an occurrence has a per-occurrence amount override (or is a loan/credit/installment occurrence whose projected amount is the computed EMI/payment, not source.amount), the stored completed transaction records the wrong projectedAmount. This makes the captured variance (actual - projected) wrong and the 'Expected Amount' shown in the modal inconsistent with what was projected. markTransactionSkippedAction (line 170-178) has the same source.amount assumption.
- Scenario: A variable monthly bill has rule amount=200 but the user set a per-occurrence override amount of 260 for the May occurrence (the calendar shows 260 projected). They mark it complete with actualAmount=260. The stored transaction records projectedAmount=200, actualAmount=260, yielding a spurious +60 variance even though the user paid exactly the amount that was projected for that occurrence. Correct projectedAmount should be 260 (the override), giving variance 0.
- Suggested fix: Resolve the occurrence's projected amount from the override (and/or the projection's paymentBreakdown) instead of always using source.amount. Look up source.occurrenceOverrides[occurrenceId]?.amount and fall back to source.amount; for loan/credit/installment types use the projected payment amount for that occurrence.
