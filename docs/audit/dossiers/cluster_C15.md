# Cluster C15

Standalone amortization: final payment not trued-up, neg-amortization drops interest, 0.01 residual, setMonth month-end overflow, mutable payment var

Source files implicated:
- app/lib/logic/amortization/loanAmortization.ts

## Member findings (from first-round analysts)

### [F62] (high/correctness) Final payment is never trued-up when monthlyPayment is provided rounded to cents, leaving a residual balance the loan never zeroes out
- File: app/lib/logic/amortization/loanAmortization.ts : 35-64
- Why wrong: The final-payment true-up only fires when `principal > balance`. When the caller supplies a real-world `monthlyPayment` that has been rounded to the cent (as lenders quote), the supplied payment is slightly LESS than the exact analytic PMT, so principal stays just below `balance` on every row including the last. The loop runs the full `termMonths` and exits because `i` reaches `maxMonths`, NOT because the balance hit zero. The reported final `remainingBalance` is a nonzero residual that is silently dropped — the loan appears to still be owed money after the full term, and no final adjusting payment is added to clear it. A correct amortizer must, on the last scheduled period (i === termMonths-1), set the final payment = remainingBalance + interest so the balance reaches exactly 0.
- Scenario: principal=20000, annualRate=6, termMonths=48, monthlyPayment=469.70 (the 469.700581 exact PMT rounded to cents). After 48 payments the code reports remainingBalance = 0.031429 and the final payment is still 469.70 (unchanged). Correct behavior: the 48th payment should be trued up to ~469.73 (467.39 principal + 2.34 interest, i.e. remaining principal + last interest) so the balance ends at exactly 0.00 and the loan is fully discharged.
- Suggested fix: Detect the last scheduled period and force a final true-up. e.g.: `const isLast = i === maxMonths - 1; if (principal > balance || isLast) { principal = balance; payment = principal + interest; }` (combined with capitalizing unpaid interest for the underpayment case), so the schedule always ends with remainingBalance === 0.

### [F63] (high/logic-error) Negative-amortization branch drops unpaid interest instead of capitalizing it, so remaining balance and total interest are understated
- File: app/lib/logic/amortization/loanAmortization.ts : 45-52
- Why wrong: When the monthly payment is less than the accrued interest (`principal = payment - interest < 0`), the code clamps `principal = 0` and then does `balance -= 0`, leaving the balance FLAT. In real negative amortization the unpaid interest (interest - payment) capitalizes and the balance GROWS. The code neither adds the unpaid interest to the balance nor records the payment shortfall, so the reported `remainingBalance` is wrong (too low) and the loan never reflects growing debt. The accrued interest beyond the payment is silently lost from the accounting (total interest summed from the schedule is understated, and the principal-paid sum is wrong). Because the balance stays flat and never crosses the termination threshold, the loan also appears to never get paid off but with a falsely constant balance.
- Scenario: principal=10000, annualRate=24 (2%/month), monthlyPayment=150, termMonths=12. Code output: every month interest=200, principal=0, remainingBalance stays exactly 10000.00 for all 12 rows. Correct: the unpaid 50/month capitalizes — balance should grow to 10050.00 after month 1, 10101.00 after month 2, ... 10670.60 after month 12. The reported balance (10000) is off by ~670 at the end and understates total interest accrued.
- Suggested fix: When `principal < 0`, capitalize the shortfall: `balance -= principal;` (subtracting a negative principal grows the balance) instead of forcing `principal = 0` then `balance -= 0`. I.e. keep `principal = payment - interest` (negative) and let `balance -= principal` increase the balance, and ensure the consumer interprets a negative principal as interest capitalization. Alternatively guard against payment <= interest at config-validation time.
- First-round verification: UNVERIFIED (verifier crashed)

### [F64] (medium/edge-case) Loop termination at balance > 0.01 leaves up to ~1 cent of principal unpaid and reports it as the final balance
- File: app/lib/logic/amortization/loanAmortization.ts : 35-60
- Why wrong: The loop guard `balance > 0.01` means the routine stops once the balance drops to a penny or less, but it never zeroes that remaining sub-cent principal nor folds it into the prior payment. For the pure analytic-PMT path the residual happens to be sub-cent and harmless, but combined with the no-final-true-up issue (and any rounded payment), the last emitted `remainingBalance` can be a stray positive value (e.g. 0.031429) that flows into PaymentBreakdown.remainingBalance and the UI as 'amount still owed'. There is no rounding of `remainingBalance` to currency precision, so floating-point dust (e.g. 1.4e-11) or pennies are surfaced as a non-zero outstanding balance.
- Scenario: Same path as principal=20000, rate=6%, term=48 but with provided payment 469.70 ends with remainingBalance=0.031429 reported to the UI / PaymentBreakdown rather than 0. Even the clean PMT path can leave floating-point dust in remainingBalance that is not rounded to cents.
- Suggested fix: On the final period, force balance to exactly 0 (see true-up fix) and round emitted monetary fields to 2 decimals, e.g. round(payment), round(principal), round(interest), and set remainingBalance = max(0, round(balance)) with an exact-zero on the last step.
- First-round verification: UNVERIFIED (verifier crashed)

### [F65] (medium/bug) currentDate advanced with Date.setMonth overflows month-end dates, producing wrong payment dates
- File: app/lib/logic/amortization/loanAmortization.ts : 62-63
- Why wrong: `Date.prototype.setMonth` rolls over when the source day-of-month does not exist in the target month. Starting from a 29th/30th/31st, advancing by one month overshoots into the following month, and the error then compounds because subsequent iterations advance from the already-corrupted date. The rest of the codebase deliberately uses dayjs `addMonths` (app/lib/utils/dateUtils.ts) specifically to get correct month arithmetic, but this module uses raw `setMonth`. The caller (loanProjections.ts) feeds `parseDate(rule.startDate)` as startDate, so a loan whose start/first-payment day is 29-31 will generate payment transactions on the wrong calendar dates, which then drives projection placement, occurrence IDs, and daily balance buckets.
- Scenario: startDate = 2026-01-31. The emitted payment dates become Jan 31, Mar 3, Apr 3, May 3, Jun 3, ... — February is skipped entirely and every subsequent payment lands on the 3rd instead of month-end. Correct (dayjs addMonths) would yield Jan 31, Feb 28, Mar 31, Apr 30, May 31. Each payment date is off by several days and the monthly cadence is broken.
- Suggested fix: Use the project's `addMonths` helper from app/lib/utils/dateUtils.ts: compute each row's date anchored to the original start day as `addMonths(base, i)`, instead of mutating with `currentDate.setMonth(...)`, to clamp to the last valid day of each month.
- First-round verification: UNVERIFIED (verifier crashed)

### [F66] (low/structure) Mutable `payment` variable is reassigned during the final-payment true-up, risking a corrupted (lowered) payment leaking into later rows
- File: app/lib/logic/amortization/loanAmortization.ts : 18-43
- Why wrong: `payment` is a single closure variable for the whole schedule, and the final-payment branch overwrites it with a reduced value (`principal + interest`). In all current paths the same row sets `balance` to 0 and the loop exits, so the lowered payment is not reused — but the design is fragile: any future change that allows the loop to continue after a partial/true-up row (or any iteration where `principal > balance` fires before the terminal period) would carry the smaller payment into all subsequent rows, understating every later payment. A regular amortization should keep the scheduled payment immutable and use a separate local for the adjusted final installment.
- Scenario: Constructed: principal=100, 0% interest, term=360, monthlyPayment=30. Rows pay 30,30,30 then row 4 fires the branch and sets the shared `payment` to 10. It happens to be terminal here, but the variable is now 10; were the loop to continue (e.g. a future negative-amortization or multi-loan reuse), every following row would incorrectly use 10 instead of 30.
- Suggested fix: Do not mutate the scheduled `payment`. Introduce a per-iteration local, e.g. `let thisPayment = payment; if (principal > balance) { principal = balance; thisPayment = principal + interest; }` and push `thisPayment` into the schedule, leaving `payment` constant.
- First-round verification: UNVERIFIED (verifier crashed)
